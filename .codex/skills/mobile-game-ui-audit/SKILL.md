# 手机游戏界面强制审核

## 强制时点与不变量

这是每次生成游戏的必经步骤，不是可选建议。

- 开始生成或修改游戏前，先读本 skill，审核目标屏幕、布局约束和安全区域来源，确定验收矩阵；向用户简短说明本轮会执行手机适配审核。
- 每次交付新游戏、更新版、试玩版或最终构建前，针对本次实际产物执行完整审核。仅数值或玩法修改也不能沿用上一版“通过”的结论。
- 为验证可以生成本地候选构建；未通过审核不能把它交付为完成版或声称适配通过。审核通过不等于获得发布、上传或提审授权。
- 稳定轴是玩法与 UI 语义；变化轴是可用视口、方向、显示缩放和系统遮挡；不变量是所有关键内容可见、可点且互不争抢触控区域。
- 适配目标面向所有受支持手机，以响应式规则与运行时安全区域适配未知机型。有限模拟矩阵不构成“所有手机实测通过”的证据。

## 1. 统一坐标与安全区域

审查设备测量 → 平台适配 → 布局 → 绘制 → 输入逆变换的完整链路。设备差异在平台边界归一化，禁止在共享布局里堆叠机型判断。

设逻辑坐标到屏幕逻辑单位的变换为 `T`，完整视口为 `V`，边缘安全区域为 `S`，额外系统遮挡集合为 `E`。所有关键文字、图标、触控区域在屏幕空间中的边界必须满足：

`T(bounds) ⊆ S ⊆ V`，且对每个 `e ∈ E` 有 `T(bounds) ∩ e = ∅`。

- `S` 来自当前方向、当前窗口的运行时安全区域，不来自分辨率或机型名称推断。灵动岛、刘海、挖孔、圆角、状态栏、底部 Home 指示条/手势区，以及宿主工具栏都要纳入审查。
- iPhone 横屏需分别验证左向与右向，不能假定左右 inset 相等。灵动岛常位于横屏侧边，不能只留顶部空白。
- 微信小游戏还需审查右上胶囊菜单等独立矩形；它不一定被 `safeArea` 包含。Web 审查 `viewport-fit`、`env(safe-area-inset-*)` 和实际 Canvas/DOM 内容矩形；其他引擎使用其当前 safe-area API。只对实际目标平台读取相应接口。
- 分清屏幕坐标、窗口坐标、CSS 像素、引擎逻辑坐标和渲染物理像素。DPR 用于清晰度，不能当成触控面积增益；相同安全边距不能扣除两次。
- Resize、旋转、全屏变化、浏览器工具栏变化和前后台恢复后，布局与输入必须消费同一份最新测量值。
- 背景与装饰可出血延伸到禁区；按钮、任务目标、生命/弹药/人质容错、关卡位置、存档状态和必要提示不可以。
- 平台无法提供遮挡数据时，把缺口记录为未验证；只有明确记录失败模型、替代方案理由及移除条件，才能增加有证据支持的临时边界适配。不能默认“没有遮挡”。

## 2. 必测设备与状态矩阵

按屏幕结构分组，不维护伪精确的机型 inset 常量。以下宽高是竖屏逻辑视口测试样例，不是设备或系统安全边距的权威数据。实际项目支持的新设备、新系统和实际可用窗口必须补充到矩阵。

| 覆盖组 | 样例逻辑尺寸 | 审核重点 |
| --- | --- | --- |
| iPhone SE / 小屏无刘海 | 320×568、375×667 | 最小可用空间、文字与触控尺寸 |
| iPhone 标准/Plus 无刘海 | 414×736 | 宽高比例和等距布局 |
| iPhone X/XS/11 系列刘海 | 375×812、414×896 | 顶部刘海与底部手势区 |
| iPhone mini / 标准刘海 | 360×780、390×844 | 窄屏与横屏侧边避让 |
| iPhone Pro / Pro Max 灵动岛 | 393×852、430×932、402×874、440×956 | 顶部及两种横屏方向的异形区 |
| 安卓小屏 / 挖孔 / 刘海长屏 | 360×640、360×800、412×915 | 不对称挖孔、导航/手势栏 |
| 折叠屏 / 多窗口 | 344×882、673×841 | 窄窗口与近方形重排，必要时避让铰链 |

- 每组测试受支持的方向，横屏左向和右向分别测；横屏锁定游戏的竖屏入口应提供安全区内的旋转提示，且不能泄漏可交互但不可见的战斗按钮。
- 除来自真实设备/模拟器的测量值，加入标明“合成压力测试”的非对称 inset、边内挖孔/胶囊矩形、狭窄安全区域。合成值不能冒称特定机型实测。
- 针对支持的浏览器、微信或原生宿主，以及可获得的 iOS/安卓版本记录测量来源；机型相同不代表不同系统和宿主的视口相同。
- 覆盖启动/加载、顶层模式选择、各玩法大厅、关卡选择、战斗 HUD、暂停、装备/商店等弹窗、剧情、成功/失败、存档继续和异常提示；只测实际存在的界面。
- 包含长名称、最大合理数字、动态按钮/列表、空状态、未解锁状态，以及切模式、旋转、恢复后的状态。父层常驻按钮与子界面必须组合检查，不能只测各自模块。

## 3. 可执行的几何与触控检查

从实际运行的布局/控件生成器读取边界，尽量复用现有测试；不要为通过审核另造一份简化布局或手抄坐标。

- 所有边界有限、宽高为正，关键内容不越界、不被裁剪、不进入安全禁区。
- 在实际屏幕逻辑单位中检查按钮触控短边：iOS 至少 44 pt，安卓至少 48 dp；移动 Web 采用 48 CSS px 的本审核基线。Canvas 要经过实际显示变换换算，不能拿内部 960×540 坐标直接判定。
- 独立动作热区不相交，热区边缘净间距至少 8 个对应屏幕逻辑单位。该间距是本审核基线，不冒称系统硬性规范；它适用于扩大的透明热区，不仅是绘制按钮。视觉分隔必须清楚。
- 间距计算使用矩形间最短距离：`dx=max(A.left-B.right,B.left-A.right,0)`，`dy=max(A.top-B.bottom,B.top-A.bottom,0)`，`gap=hypot(dx,dy)`；重叠单独拒绝。装饰性嵌套和属于同一动作的标签不作为独立按钮，但不得借此豁免不同动作。
- 空间不足时重排、分组、分页或使用明确的方向提示；不得整体缩小 UI 导致点击目标不达标，也不得扩大热区后覆盖相邻动作。
- 对每个可见控件，验证中心、近边缘、间隙及禁区的输入逆变换；命中应唯一对应其可用动作，间隙/禁区/关闭后的弹窗不得触发隐藏动作。
- 实际触控验证移动加射击等多指组合、拖出/抬起/取消、旋转及失焦后的按键释放。禁区不能被用作瞄准或其他隐形操作区。
- 对 HUD 和文字测量真实字体渲染范围，不只比较文字锚点。长标签与数字不得叠到别的字段或控件；主要操作和关键读数在最小屏幕上应可清楚辨读，不能只靠颜色传达状态。

## 4. 视觉与交互证据

几何测试、构建成功与截图检查互不替代。

1. 执行矩阵化布局与输入测试；覆盖本次修改及所有共享布局消费者。
2. 在实际浏览器/引擎候选构建上生成各屏幕结构组的代表截图，至少检查最小屏、刘海、灵动岛两个横屏方向、安卓非对称遮挡。调试图叠加禁区和热区，正式画面检查可读性与层级。
3. 打开并目视检查截图；实际走一遍本轮受影响的关键流程，检查控制台错误与触控映射。仅尺寸模拟或 Canvas 离线渲染不能验证真机的系统遮挡读取。
4. 有真机或官方模拟器时核验运行时安全区域和截图；不可用时明确记录“模拟通过，真机/特定系统未验证”，不得伪造设备实测。
5. 发现问题先定位安全区域/布局生成器/坐标变换的责任边界，再在单一源头修复并全量复测。修复仅限审核发现且属于用户授权范围的问题；保留用户明确要求的改动，保持其余 Logo、玩法数值、存档及无关内容不变。只读审核任务只能报告，修复需用户授权。

## 5. 交付门禁

在项目本轮 QA 目录保存审核记录，包含：候选版本或构建标识与源码状态、平台/系统/方向、视口与安全区域来源、页面/状态覆盖、测试命令和结果、截图路径及目视结论、发现问题与修复、未验证项。

最终状态仅为：

- **通过（注明范围）**：所列测试和视觉/交互检查全部通过，无已知阻塞问题；只声明证据支持的设备/平台范围。
- **失败**：存在遮挡、重叠、误触、过小触控目标、关键信息缺失或不可达操作。修复并重新审核后才能交付。
- **未完成**：缺少必要测试、产物或证据，不能写“通过”。可以提交代码和问题清单，但不能把游戏称为适配完成版。

未验证的目标平台安全区域读取属于该平台未完成；其他已有完整证据的平台可单独给出有边界的结论。任何影响界面或构建的后续修改会使相关审核失效，须重新执行。结尾向用户简短报告结果和未验证范围，不承诺“零 BUG”或“所有手机都已实测”。
